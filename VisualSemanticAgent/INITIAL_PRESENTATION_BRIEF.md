# 初版展示汇报材料

## 1. 项目名称

**VisualSemanticAgent：面向视障用户的医院就诊视觉动作代理**

一句话定义：

> 一个把现实世界中的通知、地点和服务信息，转成可确认、可执行系统动作的移动端视觉语义中间件。

---

## 2. 参赛方向契合点

本项目围绕“手机 AI 助手和手机系统 AI 体验”展开，重点不是做一个普通工具 App，而是探索：

- 大模型如何作为手机上的**视觉理解中间件**
- 如何把现实世界信息转成系统级动作
- 如何在移动端完成“识别 - 判断 - 执行 - 反馈”的闭环

与赛题契合的核心点：

- 使用手机相机、语音、系统 Intent 等原生能力
- 用 AI 大模型完成多模态理解和意图路由
- 面向真实移动场景，而不是纯聊天问答
- 最终形态可以落到 vivo 手机上的运行与演示

---

## 3. 应用场景定义

### 3.1 主场景

当前版本主打场景是：

**医院就诊辅助**

目标用户：

- 视障/低视力用户
- 在陌生医院环境中容易丢失关键信息的用户
- 需要快速处理通知单、导诊牌、检查单、门诊提醒的用户

### 3.2 为什么选医院

这个场景适合比赛展示，原因有四个：

- 信息密度高：时间、地点、科室、注意事项都集中存在
- 行动闭环强：识别后可以直接触发提醒或导航
- 共情价值高：评委更容易理解它的社会价值
- 技术边界清晰：可以把视觉理解、风险控制和系统执行完整讲清楚

### 3.3 典型用户问题

传统流程下，用户拿到一张医院通知，往往要经历：

1. 看通知
2. 记住时间和地点
3. 打开日历
4. 手动输入
5. 再去地图里搜索地点

对视障用户来说，这条链路几乎不可用。

我们的目标是把它压缩成：

1. 用户说“帮我看一下这个通知”
2. 系统识别并理解
3. 系统播报结果
4. 用户确认
5. 系统执行提醒或导航

---

## 4. 产品方案概述

### 4.1 不再是“拍一张图再看结果”

我们不是把产品定义成一个“识图 App”，而是定义成：

**Visual-to-Tool Agent Middleware**

它本质上做的是：

- 从现实视觉输入中抽取结构化信息
- 进行风险判断和动作选择
- 最终调用系统工具完成任务

### 4.2 核心交互原则

项目坚持三条原则：

- **先理解，再执行**
- **先解释，再确认**
- **低风险直出，高风险拦截**

这让它从“实验性识别 Demo”升级成“可解释、可控的执行系统”。

---

## 5. 典型使用链路

### 5.1 链路 A：通知单 -> 创建提醒

场景：

用户在医院门口拿到检查通知单，看不清具体时间和科室。

使用流程：

1. 用户打开应用，说“帮我看这个通知”
2. 系统识别通知中的时间、地点、事项
3. 系统播报：“识别到一条检查提醒，明天上午 9 点，门诊楼三层影像科”
4. 系统弹出确认卡片
5. 用户确认后，系统拉起日历写入待确认事件

价值：

- 降低漏看和漏记风险
- 减少跨 App 操作摩擦
- 给视障用户提供可控闭环

### 5.2 链路 B：地点信息 -> 导航

场景：

用户看到导诊牌或检查单上的地点信息，希望快速前往。

使用流程：

1. 用户拍摄或对准地点信息
2. 系统提取楼栋/科室/地点
3. 系统播报：“识别到目标地点：门诊楼三层影像科”
4. 用户确认后，系统拉起地图导航

价值：

- 把“看懂地点”直接转成“去往地点”
- 提高现实场景中的行动效率

### 5.3 链路 C：复杂说明 -> 语音摘要

场景：

用户面对大段通知、菜单或说明，不需要执行动作，只需要快速理解重点。

使用流程：

1. 用户说“读给我听”
2. 系统不逐字朗读，而是提炼重点摘要
3. 通过 TTS 直接播报

价值：

- 减少听觉疲劳
- 从 OCR 朗读升级为语义压缩播报

### 5.4 链路 D：短信草稿 -> 人在回路

场景：

用户想把当前医院状态发给家属。

使用流程：

1. 系统提取联系人号码和短信正文
2. 由于风险高，不直接发送
3. 系统只打开短信草稿界面
4. 由用户执行最后一步发送

价值：

- 防止误发
- 体现工程安全性

## 6. 技术架构

系统当前采用三层结构：

### 6.1 感知层 Perception Layer

输入来源：

- 相机画面 / 拍照结果
- 语音识别文本
- 手动输入文本

当前已有能力：

- 相机预览和拍照采集
- 语音输入
- Mock 结果回放

后续可继续增强：

- OCR 文本框定位
- 清晰度、曝光度、目标区域评分
- 连续帧自动触发

### 6.2 决策层 Decision Layer

这是本项目最重要的工程层。

它不是“模型输出什么就做什么”，而是引入了中间判断：

- Schema 解析
- 置信度融合
- 必填字段校验
- 风险阈值判定
- 澄清追问
- 确认执行

当前执行链为：

**Extract -> Suggest -> Confirm -> Execute**

### 6.3 执行层 Execution Layer

对接 Android 原生系统能力：

- 日历
- 地图
- 短信
- TTS

执行原则：

- 高风险动作不自动执行
- 中风险动作需确认
- 低风险动作可直出

## 7. 核心技术细节

### 7.1 结构化意图契约

当前模型返回格式不是自然语言，而是严格 JSON：

```json
{
  "action": "create_event | navigate | send_sms | tts_feedback | clarification | unknown",
  "confidence": 0.85,
  "payload": {
    "title": "门诊复查提醒",
    "time": "2026-05-20T14:30:00",
    "location": "门诊楼三层影像科",
    "phone_number": "13800138000",
    "description": "请提前十分钟到达",
    "answer": "这是一张医院通知"
  },
  "fallback_query": "我识别到了时间，但还不确定是上午还是下午，请补充一下。",
  "target_found": true
}
```

这样做的价值是：

- 前后端接口清晰
- 执行逻辑稳定
- 易于做风险判断和多轮追问

### 7.2 融合置信度

我们没有直接信任大模型自报的 `confidence`，而是引入了**融合置信度**：

- 模型语义置信度
- 字段完整度
- 视觉质量分
- 时序稳定度

当前代码里已经实现：

- `modelConfidence`
- `fusedConfidence`

这能帮助答辩时解释：

> 我们不是把模型输出当最终答案，而是把它当候选结果，再做客户端风控。

### 7.3 风险策略引擎

当前代码中新增了：

- `RiskPolicyEngine.kt`
- `ActionValidator.kt`

它负责：

- 判断结果是否字段齐全
- 判断是否低于阈值
- 决定是直接播报、要求确认，还是追问修复

当前策略：

- `send_sms`：高风险
- `create_event`、`navigate`：中风险
- `tts_feedback`：低风险

### 7.4 人在回路 Human-in-the-loop

系统不是“自动化替代人”，而是“帮助人做更低摩擦的确认和执行”。

体现方式：

- 中高风险动作弹出确认卡片
- 低置信度结果走 `clarification`
- 短信只生成草稿，不自动发送

### 7.5 时序稳定性

当前已实现：

- `TemporalIntentStabilizer.kt`
- `ContinuousVisionCoordinator.kt`

设计思路：

- 单帧结果不可信
- 多帧一致才进入可确认状态

这个点非常适合在答辩里强调，因为它说明项目在考虑：

- OCR 抖动
- 单帧误识别
- 低质量输入下的鲁棒性

## 10. 可直接口述的汇报摘要

我们做的是一个面向视障用户的医院就诊视觉动作代理。它不只是识别图片，而是把现实世界里的通知、地点和说明，转成结构化意图，再经过风险判断和确认流程，最终调用手机系统能力完成提醒、导航和播报。  

当前我们的核心创新点有三层：第一层是结构化语义输出，不让模型返回随意自然语言；第二层是客户端风险引擎，对置信度、字段完整性和动作风险做二次判断；第三层是人在回路机制，中高风险动作必须确认后再执行。  

从工程状态看，当前已经完成 Android 端主界面、模型 Mock 链路、风控中间件、日历/地图/短信/TTS 执行链，以及确认卡片的交互闭环。今天下午可以稳定展示“医院通知建提醒”和“科室地点去导航”两条主链路，同时也能展示高风险动作不会被自动执行这一点。
